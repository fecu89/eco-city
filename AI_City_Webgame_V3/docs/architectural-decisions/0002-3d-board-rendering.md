# ADR-0002: 도시 보드를 Three.js 3D 씬으로 렌더링

- 상태: [ADR-0003](./0003-city-kit-instanced-renderer.md)으로 대체됨 (2026-08-29)
- [ADR-0001](./0001-engine-and-stack.md)의 "Three.js는 장식용 배경에 한정" 결정을 대체.

## 결정

- 도시 보드(그리드)를 DOM 버튼 격자 대신 `src/ui/CityScene3D.js`의 Three.js 3D 씬으로 렌더링한다.
- 클릭은 레이캐스팅으로 화면 좌표 → 타일 인덱스로 환산해 기존 `onCellClick(index)` 콜백 계약을 그대로 유지한다 — 게임 로직(systems/*)은 전혀 수정하지 않았다.
- 카메라: 기본은 보기 좋은 고정 isometric 각도. OrbitControls로 드래그 회전/휠 줌은 **선택 사항**이며 플레이에 필수가 아니다 — 모바일에서 회전 제스처 없이도 탭만으로 정상 플레이 가능해야 한다는 제약을 지키기 위함.
- 일반 보드(`GridView`)와 진단 스캐너(`DiagnosisView`)는 씬을 하나만 공유하고(`initCityScene3D`는 최초 1회만 호출), `setCellClickHandler()`로 현재 단계에 맞는 클릭 콜백만 교체한다.
- 건물은 시설 타입별 색상의 단순 박스(레벨에 비례한 높이)로 표현 — 실제 3D 모델/텍스처는 쓰지 않는다.
- 선택/미리보기(인접 보너스·갈등)/진단 상태는 타일 색상·이미시브 틴트로, 시너지 링크는 건물 위 작은 정이십면체 마커로 표현한다.

## 근거

- 사용자가 실제로 배포판을 플레이해보고 "도시를 3D로 보이게 하고 싶다"고 명시적으로 요청.
- 기존에 이미 검증해둔 클릭→배치, 진단 스캔, 인접 미리보기 로직(systems/*)을 다시 만들지 않기 위해, 렌더링 계층만 교체하고 콜백 계약(인덱스 기반)은 유지하는 방식을 택함.
- 모바일 필수 요건(탭만으로 플레이 가능) 유지를 위해 카메라 회전을 선택 사항으로 설계 — 이 저장소의 다른 모든 게임과 마찬가지로 모바일 44px 탭 타겟·제스처 최소화 원칙을 따름.

## 테스트 영향

- DOM `.city-cell`/`.diagnosis-cell` 셀렉터를 쓰던 기존 테스트는 전부 깨짐 — `window.__clickCell(index)`(클릭 시뮬레이션)와 `window.__getCellVisual(index)`(시각 상태 조회) 테스트 훅으로 교체.
- 레이캐스팅 자체(화면 좌표 → 정확한 인덱스 변환)는 `tests/e2e/game.spec.js`의 좌표 기반 클릭 테스트 1개로 별도 검증 — 카메라 각도가 바뀌면 이 테스트만 다시 손보면 된다.
- WebGL 렌더링은 워커(병렬 테스트 프로세스)당 리소스 비용이 DOM보다 훨씬 커서, `playwright.config.js`의 `workers`를 낮춰야 리소스 경합으로 인한 타임아웃을 피할 수 있었다.

## 대안 검토

- **보드는 DOM 유지 + 별도 3D "미니어처" 시각화 추가**: 리스크가 더 낮지만, 사용자가 "도시를 3D로 보이게"라고 보드 자체를 지칭했고, 이미 배경용 Three.js 인스턴스가 있어 씬 관리 두 벌을 유지하는 것보다 보드 자체를 교체하는 편이 더 단순하다고 판단.
- **회전을 필수 조작으로 설계**: 더 "게임같은" 느낌을 줄 수 있으나, 모바일 탭 전용 플레이가 깨질 위험이 있어 기각. 회전은 선택적 보너스로 남김.
