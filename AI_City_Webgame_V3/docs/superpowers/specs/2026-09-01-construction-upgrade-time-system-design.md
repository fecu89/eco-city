# 건설·업그레이드 Game Clock 시스템 설계

작성일: 2026-09-01

상태: 사용자 승인 완료, 구현 전

기준 프로젝트: Three.js 기반 AI City Webgame V3

## 1. 목적

즉시 완성되던 신규 건설과 업그레이드에 짧고 예측 가능한 게임시간을 부여한다. 공사 중 발생하는 전력·수익·인력 변화와 기후 이벤트 도착 시각을 함께 보여줘 `지금 시작할지, 위기 뒤로 미룰지`를 판단하게 한다.

이 시스템은 기다리는 콘텐츠가 아니라 다음 운영 선택을 만드는 장치여야 한다.

- 여러 시설을 동시에 건설할 수 있다.
- 건설 슬롯은 없다.
- 모든 시간은 기존 Game Clock을 사용한다.
- 예측과 실제 정산은 같은 계산 코어를 사용한다.
- 공사 진행 때문에 지속적인 WebGL 렌더 루프를 만들지 않는다.

## 2. 비목표

다음 기능은 이번 범위에 넣지 않는다.

- 현실시간 기반 `setTimeout` 공사
- 게임을 종료한 동안의 오프라인 공사 진행
- 건설 슬롯·건설 인력·건설 대기열
- 공사 시작 시각을 개별적으로 예약하는 스케줄러
- 크레인 차량이나 작업자를 계속 움직이는 고비용 애니메이션
- 시설별 추가 공사 자원이나 자재 경제
- 공사 속도 연구·광고·유료 가속

## 3. 단일 시간 규칙

모든 공사와 기존 시뮬레이션은 동일한 Game Clock을 사용한다.

| 배속 | 게임시간 1시간 | 공사·연구·경제·기후 |
|---|---:|---|
| 일시정지 | 진행 없음 | 모두 정지 |
| 1× | 현실 1초 | 1시간 진행 |
| 2× | 현실 0.5초 | 1시간 진행 |
| 4× | 현실 0.25초 | 1시간 진행 |

일시정지는 생각하고 명령하는 시간이다. 일시정지 상태에서도 다음 행동을 허용한다.

- 시설 배치 계획과 일괄 착공
- 업그레이드 시작
- 공사 취소
- 정상 시설의 운영 모드 변경
- 전력 우선순위 변경
- 배터리 정책 변경
- 정보·예측 확인

## 4. 신규 건설시간

신규 시설은 시설별 고정 Game Hour를 사용한다.

| 시설 | 건설시간 | 1× 현실시간 | 4× 현실시간 |
|---|---:|---:|---:|
| 녹지 | 3h | 3초 | 0.75초 |
| 주거지 | 5h | 5초 | 1.25초 |
| 태양광 | 6h | 6초 | 1.5초 |
| 공장 | 8h | 8초 | 2초 |
| 풍력 | 8h | 8초 | 2초 |
| 순환냉각 | 8h | 8초 | 2초 |
| 데이터센터 | 10h | 10초 | 2.5초 |
| 에너지저장 | 10h | 10초 | 2.5초 |
| 화력발전 | 12h | 12초 | 3초 |
| 조력발전 | 15h | 15초 | 3.75초 |
| 핵발전 | 18h | 18초 | 4.5초 |

24시간 기후 예보 안에 가장 긴 신규 시설도 완공할 수 있다. 공장과 화력을 동시에 시작하면 공장이 8h, 화력이 12h에 각각 완공된다. 그 사이에는 현재 완공된 도시만으로 실제 운영한다.

## 5. 업그레이드 시간과 가동률

| 업그레이드 | 공사시간 | 일반 시설의 기존 성능 |
|---|---:|---:|
| Lv.1 → Lv.2 | 8h | 70% |
| Lv.2 → Lv.3 | 15h | 50% |

`기존 성능`은 목표 레벨이 아니라 `fromLevel`의 성능이다. 새 레벨 효과는 완공 틱부터 적용한다.

업그레이드도 건설 슬롯을 사용하지 않는다. 서로 다른 시설은 동시에 업그레이드하거나 신규 건설과 함께 공사할 수 있다. 단, 한 셀에는 프로젝트를 하나만 둔다.

### 5.1 일반 시설

공사 가동률을 다음 변동 항목에 적용한다.

- 발전량 또는 기능 출력
- 운영 수입
- 전력 수요
- 탄소 배출·감축
- 물 사용·절감
- 냉각 지원 효과

다음 고정 항목은 공사 가동률과 무관하게 기존 레벨의 100%를 유지한다.

- 고정 운영비
- 기존 인력 수요

### 5.2 주거지

두 업그레이드 단계 모두 기존 레벨의 다음 값을 80%로 유지한다.

- 인구 수용력
- 수입
- 전력 수요
- 물 사용

고정 운영비와 별도 고정 비용은 100%다.

### 5.3 데이터센터

두 업그레이드 단계 모두 같은 특수 규칙을 사용한다.

| 항목 | 기존 레벨 대비 |
|---|---:|
| 전력 수요 | 70% |
| 물 사용·탄소 | 70% |
| 연구 속도 | 50% |
| 수입 | 60% |
| 고정 운영비 | 100% |
| 인력 수요 | 100% |

전력 공급률이 기존 연구 가동 기준에 미달하면 연구는 기존 규칙대로 정지한다. 공사 가동률 50%는 연구가 실제 가동되는 경우의 속도 배율이다.

### 5.4 에너지저장

- 기존 저장 에너지와 에너지 구성은 유지한다.
- 기존 레벨 최대 용량을 유지한다.
- 충전 처리량과 방전 처리량은 각각 50%다.
- 보조 전력 수요, 고정 운영비, 인력 수요는 100%다.
- 기존 레벨의 저장 허브·송전 손실 완화 기능은 유지한다.
- 새 용량·정책·기술 효과는 완공 틱부터 적용한다.

### 5.5 발전소

화력·핵·태양광·풍력·조력은 기존 레벨의 발전량, 탄소, 물에 해당 업그레이드 단계의 공사 가동률을 적용한다. 고정 운영비와 인력은 100%다.

## 6. 프로젝트 상태 모델

타일은 착공 즉시 점유되어야 하므로 공사 정보는 해당 `cell`에 둔다.

```js
cell.project = {
  kind: 'build' | 'upgrade',
  fromLevel: 1,              // upgrade에만 존재
  toLevel: 2,                // upgrade에만 존재
  elapsedHours: 5,
  durationHours: 8,
  paidCost: 6,
  suspendedOperationMode: 'eco'
};
```

### 6.1 신규 건설 셀

- 시설 `type`과 목표 `level: 1`은 기록한다.
- `project.kind === 'build'`이면 시설 허가와 타일 점유에는 포함한다.
- 모든 운영 계산에서는 건설 현장으로 취급한다.
- 완공 전 성능, 수입, 전력, 탄소, 물, 운영비, 인구, 인력, 인접 효과는 모두 0이다.
- 완공 전 시설 수 기반 과밀 비용, 공장-주거 오염 인접쌍, 건강비, 환경 보너스의 계산 대상에도 포함하지 않는다.
- 완공 전 퀘스트·목표·핵발전 예비력·연구 시설 보유 조건에 포함하지 않는다.

### 6.2 업그레이드 셀

- `cell.level`은 완공 전까지 `fromLevel`을 유지한다.
- 프로젝트 프로필이 기존 레벨 성능에 공사 배율을 적용한다.
- 기존 시설로서 허가·타일·예비력에는 계속 포함한다.
- 목표 레벨은 완공 틱에만 적용한다.
- 한 셀에는 프로젝트를 하나만 둘 수 있다. 신규 건설 중 업그레이드·철거, 업그레이드 중 재강화·철거는 허용하지 않는다.

## 7. 착공과 일괄 건설

기존 일괄 건설의 원자적 확정을 유지한다.

```text
계획 작성
→ 최종 완공 도시 검증
→ 시간별 위험 예측
→ 사용자 확인
→ 모든 프로젝트 동시 착공
```

착공 시 한 번에 처리한다.

- 실제 결제 비용 전액 차감
- 모든 타일 점유
- 시설별 허가 수 점유
- 최종 도시의 인력과 시설 의존성 검증
- 각 셀에 독립된 공사 프로젝트 생성
- 임시 건설 계획 제거
- 즉시 자동저장

각 프로젝트의 `paidCost`는 해당 셀의 지역 할증, 스트레스 테스트 긴급공사 할증, 적용 할인을 반영한 실제 개별 결제액이다. 전체 차감액은 개별 `paidCost`의 합이며, 합계와 개별 비용은 같은 크레딧 반올림 규칙을 사용해 서로 달라지지 않게 한다.

어느 한 항목이라도 실패하면 크레딧, 타일, 프로젝트를 하나도 변경하지 않는다.

### 7.1 최종 검증과 중간 운영의 차이

- 착공 허용 여부는 모든 계획이 완공된 최종 도시를 기준으로 판단한다.
- 실제 운영은 현재 완공된 시설만으로 인구·인력·전력·인접 효과를 계산한다.
- 일시적인 중간 인력 부족은 허용하며 실제 산업 가동률이 감소한다.
- 최종 도시에서도 인력이 부족한 계획은 착공할 수 없다.
- 같은 계획에 의존 시설이 있으면 착공은 허용하지만, 미완공 시설의 의존 효과는 적용하지 않는다.

이미 진행 중인 다른 프로젝트가 있는 상태에서 새 계획을 확정할 수도 있다.

- 진행 중인 공사 셀은 새 계획의 배치 대상으로 사용할 수 없다.
- 시설 허가는 진행 중인 신규 공사를 이미 점유된 수로 계산한다.
- 최종 도시 검증은 기존 공사의 목표 상태와 새 계획이 모두 완공된 상태를 사용한다.
- 시간별 예측은 기존 프로젝트의 남은시간과 새 프로젝트의 전체 시간을 함께 진행한다.
- 새 계획 확정으로 비용이 다시 차감되는 대상은 새 프로젝트뿐이다.

### 7.2 업그레이드 착공

업그레이드 확인 뒤 다음을 하나의 원자적 작업으로 처리한다.

- 현재 레벨, 목표 레벨 허가, 해금 조건, 보유 크레딧, 기존 프로젝트 유무 재검증
- 업그레이드 실제 결제액 전액 차감
- 현재 운영 모드를 `suspendedOperationMode`에 보존
- `elapsedHours: 0`인 업그레이드 프로젝트 생성
- 즉시 자동저장

목표 레벨이 요구하는 최종 인력을 감당하지 못하는 업그레이드는 시작할 수 없다. 다만 주거 업그레이드의 80% 인구처럼 공사 가동률 때문에 생기는 일시적 인력 부족은 허용하고 예측창에서 경고한다.

## 8. 완공과 정산 순서

한 게임시간 틱은 다음 순서를 따른다.

```text
1. 게임시간 +1
2. 모든 project elapsedHours +1
3. progress >= 100% 프로젝트 완공
4. 새 시각의 기후 이벤트 상태 갱신
5. 현재 인구·인력 계산
6. 정상/건설/업그레이드 운영 프로필 결정
7. 발전량·전력수요 계산
8. 전력망과 배터리 정산
9. 수입·운영비 정산
10. 탄소·물 정산
11. 연구 진행
12. 퀘스트·선택 목표 판정
13. 탄소 위기·운영 위험·스트레스 테스트 판정
14. UI 전환 이벤트 반환
15. 필요한 경우 자동저장 요청
```

완공은 같은 틱의 모든 운영 정산보다 우선한다. 예를 들어 `elapsedHours = 7 / 8`인 Lv.1→2 업그레이드는 다음 틱에 먼저 Lv.2가 되고, 그 틱 전체를 Lv.2 100%로 정산한다.

신규 시설도 완공되는 순간부터 설정된 고정 운영비와 인력 효과를 적용한다. 그 틱에 전력을 전혀 받지 못해 생산·수입이 0이더라도 고정 운영비와 인력 수요를 0으로 만들지 않는다.

이벤트도 해당 시각의 전력 계산보다 먼저 갱신한다. 14:00에 폭염이 시작하면 14:00 정산부터 폭염 효과를 적용한다.

## 9. 업그레이드 운영 모드

업그레이드 시작 시 현재 운영 모드를 `suspendedOperationMode`에 저장한다.

- 공사 중 해당 시설의 운영 모드 효과와 자동 모드 전환을 무시한다.
- 해당 시설의 운영 모드 선택 UI는 잠근다.
- 공사 가동률만 적용한다.
- 전력 우선순위는 변경할 수 있다.
- 배터리는 기존 정책을 유지하며 변경도 허용한다.
- 다른 정상 시설의 운영 모드는 자유롭게 변경할 수 있다.
- 완공 또는 취소 시 저장한 운영 모드를 자동 복원한다.

## 10. 취소와 환급

환급은 지역·스트레스 할증과 적용 할인을 모두 반영한 실제 `paidCost`를 기준으로 한다.

| 진행 구간 | 환급률 |
|---|---:|
| `0% ≤ progress < 25%` | 80% |
| `25% ≤ progress < 75%` | 65% |
| `75% ≤ progress < 100%` | 50% |
| `progress ≥ 100%` | 취소 불가 |

경계는 부동소수점 비율 비교 대신 정수 시간 교차 곱으로 판정한다.

```js
if (elapsedHours * 4 < durationHours) refundRatio = 0.8;
else if (elapsedHours * 4 < durationHours * 3) refundRatio = 0.65;
else refundRatio = 0.5;
```

환급액은 `roundCredits(paidCost * refundRatio)`로 계산한다.

### 10.1 신규 건설 취소

- 건설 현장을 제거한다.
- 타일과 시설 허가를 즉시 반환한다.
- 해당 프로젝트의 진행시간은 복구하지 않는다.
- 신규 시설 효과는 애초에 0이므로 별도 운영 복구가 없다.

### 10.2 업그레이드 취소

- 프로젝트만 제거한다.
- 기존 레벨 성능을 즉시 100%로 복구한다.
- 저장했던 운영 모드를 복원한다.
- 연구 진행도와 배터리 저장량은 유지한다.
- 취소로 잃은 비용은 완성 시설의 투자 원가에 포함하지 않는다.

신규 건설 또는 업그레이드가 완공되면 `project.paidCost`는 더 이상 취소 환급에 사용하지 않는다. 이후 철거 환급은 프로젝트 환급식이 아니라 기존의 일반 철거·투자원가 규칙을 그대로 따른다.

완공 판정과 취소 요청이 같은 자바스크립트 실행 순서에 도달하면 틱의 완공 판정을 우선한다. 완공 후에는 공사 취소 대신 기존 일반 철거만 가능하다.

## 11. 공사 중 시설 선택

신규 건설 현장을 선택하면 일반 시설 콘솔 대신 공사 상세를 연다.

- 시설명과 공사 종류
- 현재 3D 단계
- 진행시간과 남은 게임시간
- 현재 환급률과 정확한 환급액
- 예상 완공 시각
- 기후 이벤트 전 완공 여부
- 공사 취소 버튼

업그레이드 현장은 기존 시설 콘솔을 유지하되 다음을 추가한다.

- `Lv.1 → Lv.2` 또는 `Lv.2 → Lv.3`
- 공사 가동률과 현재 제한 성능
- 남은시간과 취소 환급
- 운영 모드 잠금 설명
- 업그레이드 취소 버튼

공사 중에는 일반 철거 버튼을 표시하지 않는다.

## 12. 순수 예측 시뮬레이션

실제 예측 결과와 실제 공사 결과가 다른 규칙을 사용하면 안 된다. 실제 정산 코어를 예측에도 사용한다.

권장 인터페이스는 다음과 같다.

```js
advanceSimulationHour(state, {
  mode: 'live' | 'prediction'
});
```

이 함수는 전달받은 상태만 변경하고 UI·저장·오디오 같은 외부 부작용을 직접 발생시키지 않는다. 실제 게임에서는 반환된 전환 결과를 오케스트레이터가 EventBus와 저장 시스템에 전달한다. 예측에서는 복제된 상태만 변경하고 반환값을 수집한다.

퀘스트·연구 완료처럼 정산 결과에 영향을 주는 메타 전환도 계산 코어는 `wouldComplete`, `rewardDelta` 같은 전환 결과로만 반환한다. 라이브 오케스트레이터는 이를 실제 상태에 적용하고, 예측 어댑터는 예측 복제본에만 조용히 적용한다. 따라서 예측 최종 크레딧과 연구 효과는 실제 진행과 일치하지만, 실제 퀘스트 완료·보상·알림·저장은 발생하지 않는다.

### 12.1 예측 모드 허용 항목

- 공사 진행과 완공
- 게임시간과 기후 상태
- 결정적 풍력·태양광 패턴
- 이벤트 스케줄과 이벤트 효과
- 현재 운영 모드와 우선순위
- 발전량·전력수요·송전 손실
- 배터리 충전·방전·저장 구성
- 인구·인력과 산업 가동률
- 수입·운영비·탄소·물
- 연구 진행과 완료된 연구의 운영 효과

### 12.2 예측 모드 금지 항목

- 실제 `GameState` 변경
- 실제 퀘스트·목표 완료 상태 변경
- 실제 보상 지급
- 업적 처리
- EventBus·UI 이벤트 발행
- 토스트·모달·사운드
- 자동저장
- 실제 게임오버 전환

위 금지는 실제 상태와 외부 효과에 대한 규칙이다. 일치 검증에 필요한 퀘스트·연구·위기 전환은 복제본 안에서만 계산할 수 있으며, UI에는 `예상` 상태로만 표시한다.

예측용 상태 내부의 시간·배터리·연구·공사 상태는 계산을 위해 변경할 수 있지만 실제 상태에는 절대 반영하지 않는다.

### 12.3 복제해야 하는 상태

예측 스냅샷은 최소한 다음 상태를 정확히 복제한다.

- 현재 게임시간과 `tickIndex`
- 기후 상태와 이벤트 스케줄·활성 이벤트·현재 이벤트 지표
- 풍력 패턴 위치
- 배터리 저장량과 저탄소/화석 구성
- 전력 우선순위와 운영 모드
- 연구 작업과 완료 기술
- 현재 공사 프로젝트
- 확장 지역·지역 특성·스트레스 테스트 상태
- 탄소 압력에 필요한 현재 누적 상태

Set과 중첩 객체를 보존하는 정식 상태 직렬화·복원 경로로 복제하고 얕은 복사를 사용하지 않는다.

### 12.4 동적 예측 구간

`18`을 직접 사용하지 않고 계획 또는 공사 중 프로젝트의 최대 남은시간을 사용한다.

```js
predictionHorizon = Math.max(
  0,
  ...projects.map((project) => project.durationHours - project.elapsedHours)
);
```

현재 최대값은 핵발전 신규 건설의 18h지만, 향후 더 긴 시설이 생겨도 예측 코드를 바꾸지 않는다.

착공 전 계획은 아직 `cell.project`가 아니므로 예측 복제본에 `elapsedHours: 0`인 가상 프로젝트로만 삽입한다. 예측이 끝나면 이 복제본을 폐기한다.

## 13. 착공 전 타임라인

일괄 건설 확인창은 모든 시간을 나열하지 않고 상태가 바뀌는 완공 시점만 표시한다.

```text
현재
전력 +2.4E · 순수익 +0.50 · 인력 3명 여유

8시간 후 · 공장 완공
전력 -1.6E · 순수익 -0.20 · 가동률 63%
⚠ 전력 부족 · 일시적 적자 · 인력 부족

10시간 후 · 배터리 완공
배터리 0 / 20E
⚠ 저장 전력이 비어 있음

12시간 후 · 화력발전 완공
전력 +9.4E · 순수익 +1.00
✓ 정상 운영 예상
```

표시 항목:

- 전력 여유와 필수시설 공급률
- 순수익
- 인력 여유 또는 산업 가동률
- CO₂와 물
- 배터리 저장량
- 완공 시설
- 예보 이벤트와 겹치는 위험 구간

모바일 기본 화면은 최종 결과와 가장 위험한 구간 하나를 보여준다. `전체 건설 타임라인 보기`에서 모든 변화 시점을 펼친다.

모든 예측에는 `현재 운영 모드와 예보가 유지된다는 가정`을 표시한다.

## 14. 업그레이드 확인창

업그레이드 시작 전에 현재, 공사 중, 완공의 세 상태를 비교한다.

```text
핵발전 Lv.1 → Lv.2 · 8h

                 현재    공사 중   완공
발전량           19E     13.3E     28.1E
도시 전력 여유   +3E     -2.7E     +12.1E
물               5       3.5       5.8
고정 운영비      1       1         새 Lv.2 값

⚠ 완공 2시간 전에 폭염이 시작됩니다.
⚠ 해당 구간의 필수시설 공급률 최저 74%
```

예측 경고를 확인한 뒤에만 비용을 차감하고 업그레이드를 시작한다.

## 15. 혼합형 3D·진행 바 표현

채택안은 `3D 공사 단계 + 작은 상태 표식 + 선택형 상세 진행 바`다.

### 15.1 신규 건설 3D 단계

| 진행률 | 표현 |
|---|---|
| 0~30% | 기초 슬래브와 공사 표식 |
| 30~70% | 저비용 골조·비계 |
| 70~100% | 반투명 완성 외형과 비계 |
| 완료 | 비계 제거, 실제 모델, 짧은 완공 효과 |

### 15.2 업그레이드 3D 단계

- 기존 레벨 모델을 유지한다.
- 신규 건설과 다른 주황색 비계·공사 테이프를 겹친다.
- 목표 레벨 외형은 완공 전에 표시하지 않는다.
- 완공 틱에 기존 레벨에서 새 레벨의 크기·색상으로 짧게 전환한다.

### 15.3 월드 표식과 상세 바

모든 공사 시설에는 작고 재사용 가능한 표식을 표시한다.

- 신규 건설: 청록색 `⚒`
- 업그레이드: 주황색 `↑`
- 작은 원형 테두리로 대략적인 진행률 표시
- 이벤트 전에 완공되지 않는 시설: 빨간 경고 표시

상세 진행 바는 다음 우선순위로 최대 2개만 표시한다.

1. 선택한 시설
2. 데스크톱에서 현재 hover 중인 시설
3. 선택 시설이 없을 때 가장 먼저 완공될 시설 하나

상세 바는 카메라를 향하는 DOM 오버레이로 구현한다.

```text
⚒ 골조 · 주거지
██████░░░░ 3 / 5h
완공까지 2시간
```

```text
↑ Lv.1 → Lv.2
████░░░░░░ 3 / 8h
가동률 70% · 전력 여유 -2.4E 예상
```

모바일에서는 터치로 선택한 시설의 월드 바 하나와 하단 공사 상세에 같은 정보를 표시한다.

### 15.4 렌더 성능

- 공사 단계가 임계값을 넘거나 프로젝트가 시작·취소·완공될 때만 3D 장면을 dirty 처리한다.
- 진행 바는 DOM/CSS로 처리한다.
- 한 틱의 값 변경에만 짧은 CSS width 전환을 사용한다.
- 공사 진행을 이유로 60fps WebGL 루프를 유지하지 않는다.
- 비계·기초·표식은 사전 할당한 geometry/material/InstancedMesh 또는 제한된 DOM 풀을 재사용한다.
- 기존 대표 도시 24 draw calls 이하와 GPU buffer 재사용 계약을 유지한다.

## 16. 저장 v7

저장 버전을 v7로 올린다.

- `cell.project`를 검증·직렬화한다.
- 게임시간·진행시간·총시간·실제 비용·기존/목표 레벨·운영 모드를 저장한다.
- 배터리 저장 구성과 연구 작업은 기존 저장 구조로 보존한다.
- 착공·취소·완공·업그레이드 시작·취소·완료 시 즉시 저장한다.
- 기존 주기 자동저장도 유지한다.
- 현실 시각은 저장하지 않는다.

같은 틱에 여러 시설이 완공되거나 여러 전환이 발생하면 모든 전환을 먼저 반영한 뒤 자동저장은 한 번만 수행한다.

### 16.1 v6 → v7

- 모든 기존 시설은 현재 레벨의 정상 완공 상태로 유지한다.
- `project`는 모두 `null`이다.
- 운영 모드, 우선순위, 배터리 정책, 저장량, 연구를 그대로 유지한다.
- 기존 사용자 도시에 가상의 공사 상태를 만들지 않는다.

잘못된 프로젝트 데이터는 정상 셀을 훼손하지 않고 프로젝트만 제거한다. 신규 건설 프로젝트 데이터가 복구 불가능하면 해당 건설 현장만 비우고 로드 경고를 기록한다.

업그레이드 프로젝트가 손상되면 `fromLevel`인 현재 레벨과 저장된 운영 모드는 보존하고 프로젝트만 취소된 상태로 복구한다. 손상된 프로젝트를 완공 처리하거나 환급을 생성하지 않는다.

## 17. 이벤트와 UI 전환

공사 코어는 전환 결과만 반환하고 직접 이벤트를 발행하지 않는다.

필요한 전환:

- 건설 시작
- 업그레이드 시작
- 공사 단계 변경
- 신규 시설 완공
- 업그레이드 완공
- 신규 건설 취소
- 업그레이드 취소

오케스트레이터가 실제 모드에서만 EventBus, 효과음, 토스트, 3D 모션, 자동저장을 연결한다. 예측 모드에서는 이 연결을 실행하지 않는다.

## 18. 접근성

- 진행 바에 `role="progressbar"`, 현재값, 최솟값, 최댓값을 제공한다.
- 색상뿐 아니라 `⚒ 건설`, `↑ 강화` 문자와 아이콘으로 상태를 구분한다.
- 위험은 빨간색뿐 아니라 경고 아이콘과 설명을 함께 제공한다.
- 모바일 터치 영역은 최소 44px을 유지한다.
- 동작 줄이기 환경에서는 완공·레벨 전환 애니메이션을 생략하고 최종 상태만 표시한다.

## 19. 필수 회귀 테스트

### 19.1 프로젝트 수명주기

- 신규 건설은 착공 즉시 비용·타일·허가를 점유한다.
- 신규 건설은 완공 전 모든 운영 효과가 0이다.
- 여러 시설은 독립 시간으로 동시에 진행한다.
- 일시정지에서는 진행하지 않고 1×/2×/4×에서 같은 게임시간 결과를 낸다.
- 완공 후 설정된 운영비와 인력 효과가 전력 부족 여부와 무관하게 적용된다.
- 미완공 시설은 과밀·오염 인접쌍·건강비에도 포함되지 않는다.
- 이미 공사가 진행 중일 때 추가 일괄 계획을 확정하면 기존·신규 프로젝트가 독립적으로 함께 진행된다.

### 19.2 완공 경계

```text
elapsed = 7 / 8
다음 tick
→ elapsed = 8
→ Lv.2 적용
→ Lv.2 100%로 정산
```

같은 틱이 Lv.1×70%로 정산되면 실패다.

### 19.3 취소 경계

- 25% 미만: 80%
- 정확히 25%: 65%
- 75% 미만: 65%
- 정확히 75%: 50%
- 100%: 취소 UI와 취소 명령 모두 거부
- 환급은 `paidCost`를 기준으로 센트 단위 반올림

### 19.4 공사 가동률

- 일반 Lv.1→2 70%, Lv.2→3 50%
- 주거 인구·수입·수요·물 80%
- 데이터센터 수요·물 70%, 연구 50%, 수입 60%
- 배터리 저장 유지, 기존 용량 유지, 충·방전 50%
- 발전소 출력·탄소·물 공사 가동률
- 업그레이드 운영비·인력 100%
- 운영 모드 무시와 완공·취소 후 자동 복원

### 19.5 중간 완공

- 최종 인력은 충분하지만 중간 인력이 부족한 일괄 계획도 착공 가능
- 실제 중간 산업 가동률은 현재 완공 인구로 감소
- 미완공 냉각·저장·발전 시설은 인접·예비력 효과 없음
- 완공되는 틱부터 효과 적용

### 19.6 예측과 실제 일치

동일한 저장 상태를 둘로 복제한다.

```text
A: 동적 예측 구간까지 prediction 실행 → P
B: 같은 시간만큼 live 정산 코어 실행 → R
```

다음을 허용 오차 내에서 동일하게 비교한다.

- 전력 공급·수요·필수시설 공급률
- 순수익과 최종 크레딧
- 인구·인력·산업 가동률
- CO₂와 물
- 배터리 저장량과 에너지 구성
- 연구 진행량과 완료 상태
- 프로젝트 진행과 완공 시설 상태
- 활성 기후 이벤트

예측 과정에서 실제 상태, 이벤트 수, 저장 호출, 보상, 토스트, 사운드가 변하지 않아야 한다.

예측 복제본에서 발생한 가상 퀘스트·연구·위기 전환까지 반영한 결과를 비교하되, 실제 `GameState`와 외부 효과 호출 횟수는 예측 전후 완전히 같아야 한다.

### 19.7 UI·시각·성능

- 데스크톱 hover와 선택 우선순위
- 모바일 터치 상세와 전체 타임라인 펼치기
- 화면 상세 바 최대 2개
- build/upgrade/위험 표식의 비색상 구분
- 0~30%, 30~70%, 70~100% 단계 경계
- 저장 후 같은 3D 단계와 남은시간 복원
- 공사 진행 중 idle WebGL 연속 렌더 없음
- 대표 37칸 도시 24 draw calls 이하
- 미리보기·HUD 전환·공사 단계 변경에서 GPU buffer 재사용

## 20. 완료 조건

다음 조건을 모두 충족하면 구현 완료로 본다.

1. 신규 건설과 업그레이드가 단일 Game Clock에서 정확히 진행된다.
2. 일괄 건설의 각 시설이 독립적으로 완공된다.
3. 완공 틱에 새 성능이 정산보다 먼저 적용된다.
4. 공사 가동률, 운영비, 인력, 특수시설 규칙이 승인안과 일치한다.
5. 취소 환급 경계와 저장 복원이 정확하다.
6. 예측과 실제가 같은 계산 코어를 사용하고 결과 일치 테스트를 통과한다.
7. 기후 이벤트 도착 전 미완공 위험을 확인창에서 알 수 있다.
8. 혼합형 3D 단계와 선택형 진행 바가 데스크톱·모바일에서 읽힌다.
9. 기존 캠페인 두 경로와 전체 회귀 테스트가 통과한다.
10. 기존 WebGL 성능 예산을 유지한다.
